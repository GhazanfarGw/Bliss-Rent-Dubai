This report covers the expanded Phase 7 respecification you sent after the original "Rental Extension & Extension Payments" work was already reported: a second, customer-facing self-service request channel; a booking-reassignment engine that reassigns a conflicting future booking to a replacement vehicle instead of rejecting the extending customer; and a configurable late-extension penalty, independent from the existing extension-pricing configuration. 3. New functionality

  • A second, customer self-service request channel (verified by booking reference + vehicle number), landing in the same booking_extensions table as a requested row that does not auto-process.
  • A booking-reassignment conflict-resolution engine: when extending the exact vehicle would collide with a future booking on that same vehicle, the system searches for a suitable replacement vehicle for the future booking, reserves it safely, and moves it — instead of rejecting the extending customer or substituting their vehicle.
  • A new, independently configurable late-extension penalty mechanism (owner decision still pending — see §13, §26).
  • Full traceability for a vehicle reassignment (vehicle_reassignments) and domain-level customer-notification state (booking_notifications) for the affected customer.
  • An explicit admin rejection action for a customer-submitted request, since it no longer auto-resolves to rejected the way the old admin-channel conflict case did.

4. Frontend extension flow

New route /extend-rental (ExtendRentalPage.tsx), linked from both the booking confirmation page and the "manage my booking" page. Two steps, exactly as specified:

  1. Verify — the customer enters their booking reference and the vehicle's plate number (not email — a deliberately different, stronger check than the existing manage-booking lookup). A mismatch on either field produces the exact same generic message; the screen never reveals which one was wrong.
  2. Request — once verified, the customer picks a new return date and submits. There is no advance-notice window: 1 day before return, 5 days before, or already past the return date are all accepted (the last is simply flagged is_late). Submission shows a "request submitted, pending review" confirmation — never an instant approval, never a changed booking.

The customer cannot modify booking dates, vehicle, payment status, or extension status directly — every mutation is server-side, via the Edge Function and its underlying SQL function only.

5. WhatsApp/support flow

Unchanged in spirit, tightened per the new spec: support now verifies both the booking reference and the vehicle number (previously only the reference/booking itself was relied on) before an admin records the request. The admin-facing form (RentalExtensionsSection.tsx) is unchanged for this path — it still records and can immediately process a confirmed request. Both channels run through the exact same request_booking_extension() function; nothing about the extension business logic is duplicated for WhatsApp.

6. Verification mechanism

verify_booking_for_extension() (read-only, guest-callable) and submit_extension_request_public() (the actual insert, service-role only) both match on upper(left(replace(booking_id::text,'-',''),8)) = reference_suffix AND plate_number = vehicle_number (whitespace/case-insensitive), and both return zero rows / raise the identical generic error on any mismatch — the same indistinguishable-failure shape as Phase 6's get_booking_by_reference(). Neither can be used as an oracle to test whether a reference or a vehicle number exists on its own.

7. Availability logic

Unchanged core rule, reaffirmed: every check is against the exact vehicle_id, never the model, make, or category. The existing check_vehicle_availability_for_extension() preview is untouched. The real, race-safe guarantee remains bookings_no_overlap, applied at the moment bookings.end_date or bookings.vehicle_id is actually updated — never at the pre-check stage.

8. Future-booking conflict handling

New function resolve_extension_conflict(). When extending the exact vehicle would overlap a future non-cancelled booking on that same vehicle, the engine does not reject outright. It looks for a replacement vehicle for the future booking (never the extending customer's vehicle), locks the candidate row, re-checks its availability immediately before committing, and only then reassigns it. If no safe replacement exists, the extension is marked conflict_unresolved — nothing is changed, and the admin dashboard surfaces it for manual handling. This runs identically whether the extension came from the WhatsApp/support channel or the website self-service channel.

9. Replacement vehicle logic

Candidates come from available_vehicles() for the conflicting booking's own date range, ranked same model first, then same category, then any other available vehicle — excluding the vehicle already in conflict. No arbitrary downgrade, no automatic upgrade beyond the existing pricing rules (the replacement's own pricing is untouched by this phase). If ranking finds nothing available at all, the outcome is conflict_unresolved, never a silent choice.

10. Booking preservation

For the reassigned (future) booking: booking reference, customer, dates, pickup/drop-off, duration, and payment history all remain unchanged — only vehicle_id changes, recorded in a new vehicle_reassignments row (original vehicle, replacement vehicle, reason, who processed it, when). For the extending customer's own booking: the reference, per the unchanged rule from the original Phase 7 build, never changes — only end_date does. Neither party's booking reference is ever regenerated.

11. Payment/invoice

Unchanged design, reaffirmed: the extension's payment/invoice record (booking_extensions itself) stays entirely separate from the original booking's payments row. Cash still finalizes immediately; online still defers the actual end_date/reassignment commit to payment confirmation — which now also means the reassignment engine only runs once payment succeeds for an online-paid extension, so a future booking is never disturbed for an extension whose payment might still fail. No new real payment provider was introduced.

12. Pricing configuration

Unchanged from the original Phase 7 build: extension_pricing_settings.policy remains seeded NULL. Extension pricing policy remains pending owner confirmation.

13. Late penalty configuration

New, independently configurable, and deliberately left unset: extension_penalty_settings supports a fixed fee, a per-day charge, or a percentage of the extension amount — but the policy column is seeded NULL, and both the SQL layer (request_booking_extension) and the TypeScript layer (src/lib/extensionPenalty.ts) refuse to process a late extension at all until the owner sets one. Late-extension penalty calculation remains pending owner confirmation.

14. Database changes

One new migration: supabase/migrations/20260903000000_phase7_booking_reassignment.sql (not yet applied to production). It extends booking_extensions (new source, is_late, penalty_amount, penalty_policy_used, conflict_booking_id, replacement_vehicle_id, verification-audit columns; status widened from an enum to a checked text column so requested/conflict_unresolved could be added without an enum-transaction restriction), and adds three new tables: extension_penalty_settings, vehicle_reassignments, and booking_notifications. It replaces request_booking_extension() and confirm_booking_extension_payment() with versions that call the new resolve_extension_conflict() engine, and adds verify_booking_for_extension(), submit_extension_request_public(), and reject_extension_request().

17. Security/RLS

Every admin-facing mutation still checks is_admin() internally.

25. Known limitations

  • No live database in this sandbox. Every plpgsql-only behavior (conflict detection, replacement ranking, race-safety, RLS enforcement) is code-reviewed, not exercised by an automated test — see the table in §20. The migration has not been run against any real Postgres instance yet.
  • No real notification channel. booking_notifications records what should be sent; nothing actually sends it. Wiring a real provider (e.g. Resend) is a separate, later integration.
  • A customer-submitted request's dates cannot be edited during admin review — an admin can approve or reject exactly what was requested; changing the dates requires rejecting and asking the customer to resubmit. This was a deliberate scope decision to avoid ambiguity between what the customer verified and what gets approved.
  • The reassignment engine handles one primary conflicting booking per extension. If several future bookings on the same vehicle would all conflict with the extended window, the engine currently resolves the earliest one; a second overlapping booking would require a second pass. This matches every worked example in your spec (which described exactly one conflicting future booking) but is worth flagging if that scenario turns out to be more common in practice.
